# Deep Agents 每周开发约束

本项目的目标是通过亲手实现 Deep Agents 核心模块，深入理解成熟 Agent Harness 的架构设计。

> **核心原则：源码决定架构，学习决定实现深度，周计划只决定本周的功能范围。**

## 1. 官方源码优先

每次开启新一周前，必须先读取：

- `mini-repo-agent` 最新代码及对应周计划。
- Deep Agents 官方仓库中与本周任务相关的源码。
- 必要时进一步追踪 LangChain / LangGraph 底层实现。

所有设计必须有明确的官方源码依据，不能仅凭经验自行设计。

## 2. 架构严格对齐

- 模块目录、类名、函数名、函数签名、职责边界与调用链，原则上与 Deep Agents 官方保持一致。
- 可以简化功能，但不能随意改变官方架构。
- 不提前实现无关功能，也不创建没有实际用途的抽象。
- 必须区分官方实现、我们的简化实现，以及尚未实现的部分。

## 3. 先理解，再实现

每个模块按照以下顺序推进：

**官方源码 → 设计动机 → 职责边界与调用链 → 最小实现 → 验证。**

不要一开始就给出大量代码。每次只推进一个小知识点或实现步骤，由我亲手完成主要代码。

## 4. 避免偏离学习主线

- 不把 Deep Agents 项目变成普通的 LangChain / LangGraph 教程。
- 只学习当前模块所依赖的必要基础知识。
- 不重复讲解已经掌握的知识，除非涉及新的架构差异。
- 如果发现当前方案与官方不一致，先指出差异及原因，再决定如何处理。

## 5. 每周完成标准

每周结束时，检查核心功能是否运行、关键测试是否通过，以及实现是否符合 Deep Agents 对应模块的职责与接口设计。

对于有意简化的地方，明确说明与官方的区别及理由。

## 每周启动时的源码对齐分析

开始新的一周时，**先完成简短的源码对齐分析，再进入开发**，只回答三个问题：

1. **官方怎么做？** 对应哪些源码文件、类和函数？
2. **我们要实现什么？** 哪些保持一致，哪些功能暂时省略？
3. **当前代码差在哪里？** 需要修改哪些已有模块？

确认上述三点后，再按本周计划逐步实现；不要未经源码核对就提出新的目录、接口或调用链。
